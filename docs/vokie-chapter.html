Chapter 4 · Your first real app

Building Vokie

A menu bar vocabulary keeper, and a guided tour of the Swift and SwiftUI ideas that hold it together.

So far you have written Swift in playgrounds and seen SwiftUI views in previews. In this chapter we read a complete, working app from top to bottom. It's small: four source files and about 300 lines. But it touches most of the ideas you'll use every day: value and reference types, optionals, enums with associated values, protocols, property wrappers, macros, SwiftUI's data flow, and the project settings that turn source code into an app the operating system will run.

The app is called Vokie. It lives in the macOS menu bar. Click its book icon and a small panel drops down with a text field. Paste in a word, press Return, and Vokie looks the word up in the dictionary built into the Mac and adds the word and its definition to a list. When you're done, Export CSV… saves the list as a spreadsheet file you can import into flashcard apps.

A Mac app in an iOS book?

Yes, on purpose. Menu bar apps only exist on macOS, but almost everything in this chapter (Swift itself, SwiftUI, Observation, Codable, the Xcode project model, sandboxing) is the same on iPhone and iPad. Building for the Mac first lets us skip simulators and provisioning profiles while we learn. Wherever the code reaches for something Mac-only, a box like this one explains what you would use on iOS instead.

4.1The shape of an Xcode project

Open Vokie.xcodeproj and the Project navigator on the left shows this:

Vokie.xcodeproj           ← the project: build settings, targets
Vokie/                    ← the source folder
├── VokieApp.swift        ← app entry point
├── MenuBarView.swift     ← the interface
├── VocabularyStore.swift ← the data and its rules
├── DictionaryLookup.swift← wraps a system API
└── Assets.xcassets       ← app icon, accent color

Three Xcode ideas are worth getting straight now, because every Apple-platform app has them.

Project, target, product

A project is a container for settings and files. A target is one thing the project builds, such as an app, a widget, or a test bundle. The product is what the target produces. Vokie has one target, also called Vokie, and its product is Vokie.app.

An .app is not a single file. It is a folder, called a bundle, that Finder displays as one icon. Inside are the compiled executable, the resources, and a file called Info.plist that describes the app to the operating system: its name, version, identifier, and how it wants to be launched.

Folder sync

Older Xcode projects listed every source file by hand inside the project file. Newer projects, including this one, use a synchronized folder. Any .swift file you drop into Vokie/ is compiled automatically. That's why you won't see any project-file changes for the three new source files in this chapter.

The two settings that make Vokie a menu bar app

Select the project, then the Vokie target, then the Build Settings tab. Two settings were changed from the template:

SettingValueWhat it does
INFOPLIST_KEY_LSUIElementYESWrites LSUIElement = true into Info.plist. The system then runs the app as an "agent": no Dock icon, no app menu, only the menu bar item.
ENABLE_USER_SELECTED_FILESreadwriteLets the sandboxed app write to a file the user picks in a Save dialog. The template allowed read-only access, which is why CSV export needed this change.
Why it's built this way: the sandbox

The project also has ENABLE_APP_SANDBOX = YES. A sandboxed app runs inside a private container and can't touch your files unless it asks. When it needs more, it requests an entitlement: a signed permission baked into the app. "User-selected files, read-write" means: the user can grant me access to one file at a time by picking it in a system dialog. The dialog runs in a separate system process, so the user's choice is the permission. Every iOS app is sandboxed this way. On the Mac it's optional, but required for the App Store, and a good habit.

4.2Splitting the app into pieces

Before reading any code, look at how responsibilities are divided. Each file has one job, and the arrows show who knows about whom.

This is a lightweight version of a pattern you'll see described as Model–View (or MVVM, with the store as the "view model"). The useful rule is simpler than any acronym:

  • Views describe the screen and forward user actions. They hold only short-lived interface state, such as the text currently in the field.
  • The model owns the data and the rules. "No duplicates", "trim whitespace", and "save after every change" all live here, so they're true however a word gets added.
  • System APIs get wrapped. The rest of the app calls DictionaryLookup.define("word") and never sees the awkward C function underneath.

Because the store doesn't import SwiftUI, you can test it without any interface at all. While building Vokie, that's exactly how its logic was checked: a ten-line program created a store, added words, and printed the CSV.

4.3The entry point: VokieApp.swift

Vokie/VokieApp.swift
import SwiftUI

@main
struct VokieApp: App {
    @State private var store = VocabularyStore()

    var body: some Scene {
        MenuBarExtra("Vokie", systemImage: "character.book.closed") {
            MenuBarView(store: store)
        }
        .menuBarExtraStyle(.window)
    }
}

Fourteen lines, and nearly every one introduces an idea.

import SwiftUI

An import makes a module (a library of types and functions) available in this file. SwiftUI is Apple's declarative interface framework. Importing it also brings in Foundation, the general-purpose library for strings, dates, files, and so on.

@main

Every program needs one starting point. In a command-line script that's the top of main.swift. In an app you mark one type with @main, and Swift generates the startup code that creates that type and hands control to it. Only one type in a target may be @main.

struct VokieApp: App

This declares a struct named VokieApp that conforms to the protocol App. A protocol is a contract, a list of requirements a type promises to meet. App has essentially one requirement: provide a body describing the app's scenes. Meet the contract, and SwiftUI handles everything else: the run loop, events, windows.

Swift syntax: some Scene

var body: some Scene is a computed property (no stored value, just code that runs when you read it) whose type is an opaque type. some Scene means "one specific type that conforms to Scene; the compiler knows exactly which, but I'm not going to spell it out." The real type here is long and generated, something like MenuBarExtra<Label, MenuBarView> with a style modifier wrapped around it. You'll write some View constantly for the same reason.

MenuBarExtra(…) { … }: scenes and trailing closures

A scene is a top-level piece of an app's interface that the system manages. On iOS that's almost always a WindowGroup. Vokie uses MenuBarExtra, a scene that puts an item in the Mac menu bar. The first two arguments are its title (read by VoiceOver) and its icon, an SF Symbol named character.book.closed.

The { MenuBarView(store: store) } part is a trailing closure. When a function's last parameter is a closure, Swift lets you write it after the parentheses. This closure is also a view builder: a closure that lists views, which SwiftUI combines. That's why it can contain a bare MenuBarView(...) with no return.

.menuBarExtraStyle(.window): modifiers

Methods that start with a dot on their own line are modifiers. Each one returns a new, modified version of what it's attached to. The default menu bar style is an ordinary drop-down menu, which can't hold a text field. .window makes it a small floating panel that can hold any SwiftUI view.

The leading dot in .window is implicit member syntax. The parameter's type is already known, so you can write .window instead of WindowMenuBarExtraStyle.window.

@State private var store = VocabularyStore()

This line answers an important question: who owns the data? SwiftUI structs like VokieApp are cheap descriptions that SwiftUI may create and throw away many times. If we wrote a plain let store = VocabularyStore(), a new store could be created each time and the list would vanish.

@State is a property wrapper. It tells SwiftUI: "create this value once, keep it in your own storage for as long as this part of the interface exists, and give me the same one every time." The app creates the store here, at the very top, and passes it down to the view. private means no code outside this struct can touch the property.

On iOS

Replace MenuBarExtra with WindowGroup { MenuBarView(store: store) } and the rest of this file stays the same. The @main app struct, @State ownership, and scenes all work identically.

4.4The model: VocabularyStore.swift

This file contains the most Swift language features, so we'll take it in pieces.

A single entry: a struct

Vokie/VocabularyStore.swift
struct VocabularyEntry: Codable, Identifiable, Hashable {
    var id = UUID()
    var word: String
    var definition: String
    var dateAdded = Date()
}

One word in the list is a struct, a value type. Assigning a struct to a new variable copies it; changing the copy never affects the original. That's the right default for plain data like "a word and its definition".

Three protocols appear after the colon. None of them requires us to write any code, because Swift can synthesize the implementation when every stored property already supports it:

ProtocolPromiseWho needs it
CodableCan be converted to and from formats like JSONSaving the list to disk
IdentifiableHas a stable id propertySwiftUI's ForEach, to track rows as they're added or removed
HashableCan be compared and hashedSets and dictionaries; a common default for model types
Swift syntax: default values and memberwise initializers

id and dateAdded have default values; word and definition don't. Swift automatically writes a memberwise initializer for structs, and parameters with defaults become optional. So both of these work:

VocabularyEntry(word: "run", definition: "move fast")
VocabularyEntry(id: someID, word: "run", definition: "move fast", dateAdded: someDate)

Notice there are no type annotations on id or dateAdded. Swift infers UUID and Date from the values.

The store: an observable class

@Observable
final class VocabularyStore {
    private(set) var entries: [VocabularyEntry] = []
    private let fileURL: URL
    …
}

The store is a class, a reference type. Passing a class instance around passes a pointer to the same object. That's exactly what we want here: the app and the view must share one list, not each get a copy.

Why it's built this way: struct or class?

A good rule of thumb: use a struct for data that represents a value (an entry, a coordinate, a color). Use a class for something with an identity that several parts of the app share and watch for changes (a store, a network session, a document). VocabularyEntry is a value; VocabularyStore is a thing.

Three keywords shape the class:

  • @Observable is a macro, code that writes code at compile time. It rewrites each stored property so that reading it records "someone is interested" and writing it announces "this changed". When a SwiftUI view's body reads store.entries, SwiftUI notices, and redraws that view whenever entries changes. You never write a "please refresh" call.
  • final means no other class may subclass this one. It states your intent, and lets the compiler call methods directly instead of looking them up at runtime.
  • private(set) var entries means anyone can read the entries but only the store itself can change them. The view can't do store.entries.append(…) and skip the duplicate check. It has to go through add(_:). This is how the model protects its rules.

[VocabularyEntry] is Swift's shorthand for Array<VocabularyEntry>, an ordered list where every element has that type.

Results as an enum with associated values

enum AddResult {
    case added(VocabularyEntry)
    case duplicate
    case notFound
    case empty
}

Adding a word can go four ways. Many languages would return a Bool or throw an error. Swift's enums are more expressive: each case can carry its own data, called an associated value. Only .added carries the new entry, because only success has one. The view will switch over the result, and the compiler will refuse to build if any case is forgotten.

The enum is declared inside the class, so its full name is VocabularyStore.AddResult. Nesting a type inside another is how Swift groups related types without cluttering the global namespace.

The initializer, and where files go

init(fileURL: URL? = nil) {
    if let fileURL {
        self.fileURL = fileURL
    } else {
        let support = FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask)[0]
            .appendingPathComponent("Vokie", isDirectory: true)
        try? FileManager.default.createDirectory(at: support, withIntermediateDirectories: true)
        self.fileURL = support.appendingPathComponent("vocabulary.json")
    }
    load()
}
Swift syntax: optionals and if let

URL? is an optional: it holds either a URL or nil (nothing). Swift never lets you use an optional as if it definitely had a value. You have to unwrap it first. if let fileURL { … } is shorthand for if let fileURL = fileURL: "if this optional has a value, bind it to a non-optional constant named fileURL inside the braces."

The default = nil means the app calls plain VocabularyStore(), while a test can pass a temporary file path. This is a lightweight form of dependency injection.

Swift has a strict rule here: every stored property must have a value before an initializer finishes, and before you call methods on self. That's why self.fileURL is assigned in both branches of the if before load() runs. Delete either assignment and the compiler stops you.

try? calls something that might throw an error, and turns any failure into nil instead. It's used here because a failure to create the folder will show up anyway when saving fails. That's acceptable in a small app; in a larger app you'd likely report it.

Why Application Support?

Apple platforms give apps standard folders with standard meanings. Documents is for files the user thinks of as theirs. Caches can be deleted by the system. Application Support is for data the app needs but the user doesn't manage directly, which describes our JSON file. Because Vokie is sandboxed, this path quietly resolves inside its private container: ~/Library/Containers/…/Data/Library/Application Support/Vokie/.

Adding a word: guard and closures

func add(_ input: String) -> AddResult {
    let word = input.trimmingCharacters(in: .whitespacesAndNewlines)
    guard !word.isEmpty else { return .empty }
    if entries.contains(where: { $0.word.caseInsensitiveCompare(word) == .orderedSame }) {
        return .duplicate
    }
    guard let definition = DictionaryLookup.define(word) else { return .notFound }
    let entry = VocabularyEntry(word: word, definition: definition)
    entries.append(entry)
    save()
    return .added(entry)
}

Read this function top to bottom and it reads like the rules themselves: trim it; reject if empty; reject if we have it; reject if the dictionary doesn't; otherwise add, save, report success.

  • func add(_ input: String) -> AddResult: the underscore removes the argument label, so callers write store.add("run") instead of store.add(input: "run"). Inside the function the parameter is still called input. -> introduces the return type.
  • let declares a constant; var declares a variable. Prefer let, and Xcode will warn you when a var is never changed.
  • guard condition else { return … } is an early exit. It says "this must be true to continue", and the else block must leave the function. guard let unwraps an optional and, unlike if let, keeps the unwrapped value available for the rest of the function. That's why definition can be used two lines later.
  • { $0.word.caseInsensitiveCompare(word) == .orderedSame } is a closure, an unnamed function passed as an argument. $0 is shorthand for its first parameter, here each entry in turn. "Does any entry's word match, ignoring case?"

Removing, and the shared save()

func remove(_ entry: VocabularyEntry) {
    entries.removeAll { $0.id == entry.id }
    save()
}

Removal matches on id, not on the word, so it always removes exactly the row you clicked. Every method that changes entries ends by calling save(), so the file on disk always matches what's on screen.

Saving and loading with Codable

private func load() {
    guard let data = try? Data(contentsOf: fileURL) else { return }
    entries = (try? JSONDecoder().decode([VocabularyEntry].self, from: data)) ?? []
}

private func save() {
    guard let data = try? JSONEncoder().encode(entries) else { return }
    try? data.write(to: fileURL, options: .atomic)
}

This is the payoff of adding Codable to the struct: the whole array becomes JSON in one call. [VocabularyEntry].self refers to the type itself rather than a value of it, which tells the decoder what shape to expect.

?? is the nil-coalescing operator: "use the value on the left, or if it's nil, the one on the right." If the file is corrupt, we start with an empty list instead of crashing.

.atomic writes to a temporary file first, then swaps it into place. If the Mac loses power halfway through a save, you get the old file or the new one, never a half-written mix.

The CSV export: computed properties and string escaping

var csv: String {
    var lines = ["vocabulary,definition"]
    for entry in entries {
        lines.append("\(Self.csvField(entry.word)),\(Self.csvField(entry.definition))")
    }
    return lines.joined(separator: "\r\n") + "\r\n"
}

private static func csvField(_ value: String) -> String {
    "\"" + value.replacingOccurrences(of: "\"", with: "\"\"") + "\""
}

csv is a computed property: it looks like a stored value from outside (store.csv), but runs code every time it's read. That keeps it from ever falling out of date with entries.

"\(…)" is string interpolation: the expression inside is evaluated and inserted into the string. \" is an escaped quote character.

Definitions are full of commas, so every field is wrapped in quotes, and any quote inside a field is doubled. That's the CSV standard (RFC 4180), which is also why lines end in \r\n. static means the function belongs to the type, not to any one store, so it's called as Self.csvField. And since its body is a single expression, Swift lets us leave out return.

4.5Talking to the system: DictionaryLookup.swift

Vokie/DictionaryLookup.swift
import CoreServices
import Foundation

/// Looks words up in the built-in macOS Dictionary (offline, no network needed).
enum DictionaryLookup {
    static func define(_ word: String) -> String? {
        let range = CFRange(location: 0, length: word.utf16.count)
        guard let raw = DCSCopyTextDefinition(nil, word as NSString, range)?.takeRetainedValue() else {
            return nil
        }
        return clean(raw as String)
    }
    …
}

An enum with no cases

DictionaryLookup is an enum with no cases, only static functions. An enum with no cases can't be instantiated, so DictionaryLookup() is a compile error. That makes it a clean namespace: a named group of related functions. You'll see this pattern throughout Swift code.

The comment starting with /// is a documentation comment. Option-click DictionaryLookup anywhere in Xcode and this text appears in a popover.

Calling a C API from Swift

DCSCopyTextDefinition comes from Dictionary Services, part of CoreServices, a C framework that predates Swift by decades. Swift can call C directly, but C's conventions show through in three places:

  • CFRange and utf16.count. The function wants to know which part of the string to look up, measured in UTF-16 code units, the way Apple's older string types count. Swift's String counts characters by default, and those can differ: an emoji is one character but two UTF-16 units. Asking for word.utf16.count gives the C function the measurement it expects.
  • word as NSString. The function takes a CFString. Core Foundation's CFString and Foundation's NSString are toll-free bridged: the same object in memory, usable as either. Swift's String converts to NSString with as, and NSString is accepted where CFString is expected.
  • ?.takeRetainedValue(). C has no automatic memory management. The result comes back as Unmanaged<CFString>?, so Swift is telling you it doesn't know who's responsible for freeing it. Core Foundation's naming convention answers that: functions with Copy or Create in their name hand ownership to the caller. takeRetainedValue() means "I own this now; manage it for me." The ?. is optional chaining: if the function returned nil (no definition), the whole expression is nil and the guard exits.
Why wrap it?

All of that awkwardness is contained in about five lines. The rest of the app sees one clean Swift function, define(_:) -> String?. If Apple replaces this API, or you switch to an online dictionary, only this file changes.

On iOS

Dictionary Services doesn't exist on iOS. The nearest equivalent is UIReferenceLibraryViewController, which shows Apple's dictionary in its own screen but doesn't give your code the text. An iOS version of Vokie would call a web dictionary API instead, probably with URLSession and async/await. Because of the wrapper, that change would be confined to this one file.

Cleaning up the result: strings and indices

The raw text looks like this:

ephemeral e·phem·er·al | əˈfem(ə)rəl | adjective lasting for a very short time: … DERIVATIVES … ORIGIN …
static func clean(_ text: String) -> String {
    var result = text
    let pipes = result.indices.filter { result[$0] == "|" }
    if pipes.count >= 2 {
        result = String(result[result.index(after: pipes[1])...])
    }
    let tailMarkers = [" PHRASES ", " PHRASAL VERBS ", " DERIVATIVES ", " ORIGIN "]
    if let cut = tailMarkers.compactMap({ result.range(of: $0)?.lowerBound }).min() {
        result = String(result[..<cut])
    }
    return result.trimmingCharacters(in: .whitespacesAndNewlines)
}
Swift syntax: why you can't write text[5]

Coming from other languages, you might expect to index strings by number. Swift doesn't allow it, because characters can take a variable number of bytes (think é or emoji). Jumping to "character 5" would mean scanning from the start, and Swift won't hide that cost behind [5]. Instead you work with String.Index values that the string itself hands out: result.indices, result.index(after:), range(of:)?.lowerBound.

result[i...] and result[..<i] use range operators: "from i to the end" and "from the start up to, but not including, i." Slicing a string gives a Substring, a lightweight view into the original, so we wrap it in String(…) to make an independent copy.

The second step chains two collection operations. compactMap transforms each marker into "where it appears, if anywhere" and drops the nils. .min() picks the earliest position. We cut there, because whichever extra section comes first, everything after it goes.

4.6The interface: MenuBarView.swift

This is the biggest file, but it's built from a small number of repeating ideas.

The view's state

Vokie/MenuBarView.swift
struct MenuBarView: View {
    let store: VocabularyStore

    @State private var input = ""
    @State private var status: Status?
    @FocusState private var inputFocused: Bool

    private struct Status {
        var message: String
        var isError: Bool
    }
    …

A SwiftUI view is a struct that conforms to View and provides a body. Look at the three different ways this view holds data. The distinction is one of the most important ideas in SwiftUI:

DeclarationWho owns itWhy here
let store: VocabularyStoreSomeone else (the App)The view only uses the store. Because the store is @Observable, SwiftUI redraws this view when the parts of it that body reads change. No wrapper is needed.
@State private var inputThis viewShort-lived interface state: the text in the field right now. No other part of the app cares.
@FocusState private var inputFocusedThis viewA special kind of state that's linked to the keyboard focus.

Status is a tiny private struct nested inside the view, a message plus a flag for whether to show it in red. Because no other file needs it, it stays out of sight. status: Status? is optional because most of the time there's no message.

Layout with stacks

var body: some View {
    VStack(alignment: .leading, spacing: 10) {
        TextField("Paste a word and press Return", text: $input)
            .textFieldStyle(.roundedBorder)
            .focused($inputFocused)
            .onSubmit(addWord)

        if let status {
            Text(status.message)
                .font(.caption)
                .foregroundStyle(status.isError ? Color.red : Color.secondary)
                .lineLimit(3)
        }

        Divider()
        …

SwiftUI layouts are built from three stacks: VStack (top to bottom), HStack (left to right), and ZStack (front to back). Nest them, and use Spacer() to push things apart. There are no pixel coordinates and no constraints to manage.

Swift syntax: the $ prefix and bindings

text: $input doesn't pass the string. It passes a binding, a two-way connection to the @State storage. The text field reads its current value through the binding and writes back through it every time you type. input is the value; $input is the connection to the place it's stored. The same applies to .focused($inputFocused): the field updates that Bool when it gains or loses focus, and setting it to true moves focus into the field.

.onSubmit(addWord) passes the method addWord itself, not its result (note there are no parentheses). Swift functions are values, so this means "call addWord() when the user presses Return."

The if let status { … } inside the stack shows that a view builder can contain ordinary if statements. When there's no status, the Text isn't there at all. Similarly, condition ? a : b is the ternary operator, a compact if/else that produces a value.

Lists with ForEach

if store.entries.isEmpty {
    Text("No words yet.")
        .foregroundStyle(.secondary)
        .frame(maxWidth: .infinity, minHeight: 60)
} else {
    ScrollView {
        LazyVStack(alignment: .leading, spacing: 8) {
            ForEach(store.entries.reversed()) { entry in
                EntryRow(entry: entry) { store.remove(entry) }
            }
        }
    }
    .frame(maxHeight: 260)
}

This is where Identifiable pays off. ForEach builds one row per entry, and uses each entry's id to tell rows apart. When you add a word, SwiftUI can tell exactly one new row appeared and leave the others alone. reversed() shows the newest word first without changing the stored order.

{ entry in … } is a closure with a named parameter. You could write $0, but a name reads better in anything longer than one expression. LazyVStack only creates rows as they scroll into view, which matters once the list holds hundreds of words. .frame(maxHeight: 260) caps the panel's height so the list scrolls instead of growing past the screen.

Buttons, menus, and roles

HStack {
    Text("\(store.entries.count) word\(store.entries.count == 1 ? "" : "s")")
        .font(.caption)
        .foregroundStyle(.secondary)
    Spacer()
    Button("Export CSV…", action: exportCSV)
        .disabled(store.entries.isEmpty)
    Menu {
        Button("Clear All Words", role: .destructive, action: confirmClear)
            .disabled(store.entries.isEmpty)
        Divider()
        Button("Quit Vokie") { NSApp.terminate(nil) }
    } label: {
        Image(systemName: "ellipsis.circle")
    }
    …
}

A few things to notice:

  • A ternary inside string interpolation produces "1 word" but "2 words". Small details like this make an app feel cared for.
  • .disabled(store.entries.isEmpty) greys out the button when there's nothing to export. Because it reads store.entries, the button re-enables itself the moment you add a word. That's Observation at work.
  • role: .destructive tells the system this action destroys data, and the system styles it to match. You describe what it is; the platform decides how it looks.
  • Menu { … } label: { … } shows multiple trailing closures: the first has no label, and later ones are introduced by their argument label.
  • Button("Quit Vokie") { NSApp.terminate(nil) }. A menu bar app has no Dock icon and no app menu, so without this button the only way to quit would be Activity Monitor.

Turning results into messages: switch

private func addWord() {
    let word = input.trimmingCharacters(in: .whitespacesAndNewlines)
    switch store.add(word) {
    case .added(let entry):
        status = Status(message: "Added “\(entry.word)”.", isError: false)
        input = ""
    case .duplicate:
        status = Status(message: "“\(word)” is already in your list.", isError: true)
    case .notFound:
        status = Status(message: "No dictionary entry for “\(word)”.", isError: true)
    case .empty:
        status = nil
    }
}

Here the enum from §4.4 comes back. case .added(let entry) both matches the case and pulls out its associated value. Swift's switch must be exhaustive: if you later add a fifth case to AddResult, this function stops compiling until you handle it. That's a feature. The compiler shows you every place the new case needs handling.

Notice that the input is only cleared on success. If a word isn't found, it stays in the field so you can fix a typo.

Swift syntax: why can a struct's method change status?

Normally a method on a struct can't modify the struct's properties unless it's marked mutating. But status and input aren't really stored in the struct. @State keeps them in SwiftUI's storage, and the struct only holds a handle to that. Setting status writes through the handle, so no mutating is needed, and SwiftUI knows to redraw.

Stepping outside SwiftUI: AppKit panels

private func exportCSV() {
    let panel = NSSavePanel()
    panel.allowedContentTypes = [.commaSeparatedText]
    panel.nameFieldStringValue = "vocabulary.csv"
    panel.canCreateDirectories = true
    NSApp.activate()
    guard panel.runModal() == .OK, let url = panel.url else { return }
    do {
        try store.csv.write(to: url, atomically: true, encoding: .utf8)
        status = Status(message: "Exported \(store.entries.count) words to \(url.lastPathComponent).", isError: false)
    } catch {
        status = Status(message: "Export failed: \(error.localizedDescription)", isError: true)
    }
}

Names starting with NS (NSSavePanel, NSApp, NSAlert) come from AppKit, the Mac's older, object-oriented interface framework. SwiftUI is built on top of it, and you can use both in the same file. Here, AppKit's save panel gives us direct control over the dialog.

  • .commaSeparatedText is a Uniform Type Identifier (from the UniformTypeIdentifiers import). Apple platforms describe file types this way rather than by extension alone.
  • NSApp.activate() brings Vokie to the front first. A menu bar app is never the "active" app by default, so without this call the Save dialog could open behind other windows.
  • runModal() blocks until the user clicks Save or Cancel. The guard combines two checks with a comma: the user clicked OK, and a URL exists.
  • This is the moment the sandbox entitlement from §4.1 matters. The URL the panel returns comes with permission to write that one file.
Swift syntax: do / try / catch

Functions that can fail are marked throws, and every call to one must be marked try. Swift makes failure points visible in the code. Inside do { … }, a thrown error jumps to catch, where an implicit constant named error holds it. Compare this with the try? we used for saving JSON: there, failure was acceptable to ignore. Here, the user explicitly asked for an export, so they deserve to hear if it failed.

On iOS

There's no NSSavePanel on iOS. You'd use SwiftUI's .fileExporter(isPresented:document:contentType:defaultFilename:onCompletion:) modifier, or a ShareLink that offers the CSV to Files, Mail, AirDrop, and other apps. The AppKit equivalent on iOS is UIKit: UI prefixes instead of NS, such as UIApplication and UIAlertController.

Confirming a destructive action

private func confirmClear() {
    let alert = NSAlert()
    alert.messageText = "Clear all \(store.entries.count) words?"
    alert.informativeText = "This can't be undone. Export a CSV first if you want to keep them."
    alert.addButton(withTitle: "Clear")
    alert.addButton(withTitle: "Cancel")
    alert.buttons[0].hasDestructiveAction = true
    NSApp.activate()
    if alert.runModal() == .alertFirstButtonReturn {
        store.removeAll()
        status = nil
    }
}

Apple's Human Interface Guidelines ask apps to confirm actions that can't be undone, and to say what will happen in specific terms ("Clear all 42 words?" rather than "Are you sure?"). Marking the first button as destructive gives it the system's warning style.

A small reusable view: EntryRow

private struct EntryRow: View {
    let entry: VocabularyEntry
    let onDelete: () -> Void

    @State private var hovering = false

    var body: some View {
        HStack(alignment: .top) {
            VStack(alignment: .leading, spacing: 2) {
                Text(entry.word).font(.headline)
                Text(entry.definition)
                    .font(.caption)
                    .foregroundStyle(.secondary)
                    .lineLimit(2)
                    .help(entry.definition)
            }
            Spacer(minLength: 4)
            Button(action: onDelete) {
                Image(systemName: "xmark.circle.fill")
            }
            .buttonStyle(.plain)
            .foregroundStyle(.secondary)
            .opacity(hovering ? 1 : 0)
            .help("Remove")
        }
        .contentShape(Rectangle())
        .onHover { hovering = $0 }
    }
}

Splitting a row into its own view keeps MenuBarView readable, and gives each row its own @State. Each row tracks whether it is being hovered.

  • let onDelete: () -> Void is a property whose type is a function type: a function that takes nothing and returns nothing. The row doesn't know about the store. It just says "I was asked to delete," and its parent decides what that means. This callback pattern keeps small views reusable.
  • .lineLimit(2) shortens long definitions to two lines, and .help(entry.definition) shows the full text as a tooltip when you hover. That's a Mac convention.
  • .contentShape(Rectangle()) makes the whole row respond to the pointer, including the blank space between views, so hover works anywhere in the row.
  • .onHover { hovering = $0 } receives true or false as the pointer enters and leaves, and the delete button fades in and out to match.
On iOS

Touchscreens have no hover, so a hidden-until-hover button would never appear. On iOS you'd put the rows in a List and add .swipeActions { Button("Delete", role: .destructive) { … } }, so users swipe left to delete. Same idea, different platform conventions.

One more project setting: everything on the main actor

The project sets SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor. In Swift's concurrency model, the main actor represents the main thread, the only thread allowed to update the interface. This setting makes every type in the app main-actor code by default. For a small app that does all its work in response to clicks, that's exactly right, and it means you won't see concurrency warnings about the store being shared between the app and the view. When a later chapter introduces network calls, you'll learn to move specific work off the main actor with async functions.

4.9Key terms

Bundle
A folder, such as Vokie.app, that the system treats as a single item. It holds the executable, resources, and Info.plist.
Entitlement
A signed permission that lets a sandboxed app do something beyond its defaults.
Protocol / conformance
A list of requirements, and a type's promise to meet them.
Value type / reference type
Structs and enums are copied on assignment; class instances are shared.
Optional
A type that may hold a value or nil, unwrapped with if let, guard let, ?., or ??.
Associated value
Data attached to a single enum case, such as .added(entry).
Closure
An unnamed function written inline, often as a trailing closure.
Property wrapper
An attribute like @State that changes how a property is stored and accessed.
Macro
Code that generates code at compile time, such as @Observable.
Binding
A two-way connection to a piece of state, written with $.
Modifier
A method on a view that returns a modified view, such as .font(.caption).
Scene
A top-level unit of interface managed by the system: a window group, a menu bar extra.
Main actor
The concurrency context for the main thread, where all interface work happens.
Toll-free bridging
Using a Core Foundation type and its Foundation counterpart, such as CFString and NSString, interchangeably.
